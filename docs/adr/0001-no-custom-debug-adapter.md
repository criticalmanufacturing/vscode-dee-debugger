# ADR 0001 — No custom Debug Adapter; orchestrate stock coreclr attach

Status: accepted (2026-08-14)

## Context
DEE debugging works because the MES host, when an action is in per-user debug mode, recompiles
it from the developer's source file with `OptimizationLevel.Debug`, embedded source, and a PDB
whose document path is that file. Any .NET debugger attached to the host process binds
breakpoints normally. The old VS add-in just opened VS's "Attach to Process" dialog.

## Decision
Do not implement a Debug Adapter. The extension orchestrates: (1) file placement visible to the
host, (2) ActivateDebugMode registration, (3) launching a stock `coreclr` attach session
(Microsoft C# extension) with generated configuration — `pipeTransport` over
`docker exec`/`kubectl exec` for containers, plus `sourceFileMap` and `justMyCode: false`.

## Consequences
- Hard dependency on `ms-dotnettools.csharp` (declared in package.json). vsdbg licensing binds
  us to Microsoft's debugger ecosystem (same constraint the whole product dev flow already has).
- Container debugging requires `/vsdbg/vsdbg` inside the host container; the extension offers a
  one-click install (host image doesn't ship it; SYS_PTRACE is already granted in local-stack
  debug overrides).
- Enormously less code/maintenance than a DAP implementation; identical debugging fidelity.

## Erratum (2026-10-19)
"SYS_PTRACE is already granted in local-stack debug overrides" holds for the MES host's own
development compose overrides and for the cmf-dev plugin's 10.x–11.x stack templates, but **not** for its
MES 12 template (`stack/v12/compose.local.yaml`: no `cap_add`), nor for
11.x stacks generated by older plugin versions. The extension therefore probes the container and
escalates with `docker exec --privileged -u 0` when the capability is missing. The decision (stock
coreclr attach, no custom adapter) is unaffected.
